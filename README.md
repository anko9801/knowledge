幾何の連載は「仮定した構造」で分けてある。土台（ベクトル空間・微積分・位相）→
線形代数（1 点）→ ベクトル解析（$\mathbb{R}^3$、入口）→ 微分形式（計量なし）→
Riemann 幾何（計量あり）。各記事の冒頭に、その回が計量を使うかどうかを出している。

計算機の連載は「人工物ではなく、それを決めた制約」で切ってある。x86 や Linux や
Haskell は概念ではなく事例で、仕様書にそう書いてあるから正しい。連載に載るのは
「なぜその設計になるか」が言える側だけ——速い記憶は高いからメモリ階層が出る、
互いに壊せないことを要請するからアドレス空間が分かれる、という形にする。

制約は四種類ある。**機械**（速い記憶は高い、依存のある命令は重ねられない）が
「計算機の構成」を決め、**人**（同時に頭へ置ける量は決まっている）、**論理**（不正な
状態を型で作れなくできる）、**経済**（変更は時間で積分される）が「プログラムの構成」を
決める。

人と経済は入口だけが経験的なので、概念グラフでは `empirical` の辺で繋いである。
既定の経路探索には出てこない。「作業記憶は 4±1」から「goto をやめろ」は導けない
からで、そこは動機にとどまる。導けるのはその先——進行状況を有限の座標で書けるか
（Hoare 論理）、実装を替えても外から区別できないか（表現独立性）、直す箇所はどこまで
広がるか（結合関係の推移閉包）。

関数型が特別なのは、**人・論理・機械の三つから独立に同じ設計へ着く**ためである。
どれか一つに還元すると、その強みの理由の方が消える。認知負荷だけで説明しようと
すると、「純粋にすると楽」も「純粋にすると辛い」も同じ理屈で言えてしまい、
モナド変換子の $N^2$ 問題を事前に予測できない。

## 概念グラフ

記事とは別に、`src/data/concepts.ts` に**概念の依存グラフ**を置いてある。記事があるか
どうかとは無関係に「何を理解するには何が要るか」だけを書いたもので、記事はそこへの
被覆として扱う。だから、まだ書いていない領域も同じグラフに乗り、執筆計画が立つ。

```sh
npm run curriculum goals            # 到達目標と、そこまでの残り本数
npm run curriculum plan stokes      # 依存順。記事の有無つき
npm run curriculum next             # 次に書くべき記事（下流の多い順）
```

辺は論理的な依存だけで、「この順で教わるのが普通だから」という慣習は入れない。
詳細は [docs/build.md](docs/build.md)。

グラフは執筆計画だけでなく、**記事のページにも出る**。表題の下に「前提」、前後ナビの
下に「この回を前提にしている回」を、辺から機械的に引いて並べる。連載の前後は編集上の
並びにすぎないが、こちらは論理的な前後である。検索から 1 本だけ飛んできた読者が、
自分がその回を読める状態かを判断できる。

## 書き方

本文は Typst で書く。数式は MathML として出るので、画像ではなくテキストのまま
読める。選択もコピーもページ内検索もできる。同じソースから PDF も出せる。

本文には `#check[問い][答え]` で**想起の問い**を置ける。読んで分かった感覚は、
取り出せることとほとんど相関しないので、答えを畳んで一度考える機会を作る。採点も
記録もしない。いまは測度と確率の 4 回だけで試している。

ビルドの詳細は [docs/build.md](docs/build.md)。
